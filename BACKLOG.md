# Backlog

- **user_progress last-review-wins.** A restored write can overwrite newer SM-2 state from another device. Not fixed because `updated_at` is not comparable across clients: the frozen Flutter app writes local time with no timezone, so its values are off by the local offset (3h for Uruguay). The clean fix is a `reviewed_at timestamptz` column plus a `BEFORE UPDATE` trigger that keeps the row with the later `reviewed_at`. Narrow window: needs an app kill with unsent ratings AND use of another device before the next open.
- Flutter wrote `updated_at` as a local time without timezone on `user_progress` and `user_settings`, so those stored values are shifted. Only matters if we ever compare timestamps across clients.
- An English-only user is still gated on Russian text: `hasTranslations` (src/data/words.ts) requires both an English and a Russian translation for a word to enter Learn, Review and practice, whatever the translation switches say. Left alone on purpose when the switches were made to govern what is shown: changing it changes which words are learnable (and the pool sizes, the daily counts and the Matching and Cloze eligibility with it), which is a separate decision. Today every dictionary word has both, so it only bites for custom words with one translation.
- **Re-adding a deleted custom word revives its old progress.** Deleting a custom word removes only its `user_words` row; its `user_progress`, `user_favorites` and `user_hidden_words` rows are left, as the Flutter app leaves them. Adding the same word again (same `es_word`) therefore brings back the old repetitions, schedule, star and hidden flag. Left alone to stay compatible with the Flutter app; a clean delete would also remove those rows.
- **A deleted custom word can come back from a Flutter device that still holds it.** The Flutter app pushes every custom word it has locally on each sync and its pull never deletes a local word that is missing from the cloud, so a device that had the word before it was deleted elsewhere (here, or on another Flutter device) writes it back. The tombstone in `pending_word_deletes` only stops that app's pull from resurrecting a word it deleted itself.
- **Custom words lose their inflected word form.** `word_form_in_example` has no column in `user_words`, so the form the enrichment returns is thrown away on the web and is never synced. The web highlights (and the Cloze blanks) a custom word only where the sentence contains it as typed; an inflected form ("Tengo" for "tener") is not found, and a Rioplatense form never becomes the headword. Fixing it needs a new column on a table the Flutter app also uses.
- **High priority — FSRS instead of SM-2.** Anki has moved from its SM-2 variant to FSRS, a model of memory (difficulty, stability, and the chance of remembering at a given moment) fitted on a very large corpus of real reviews. It predicts forgetting better than SM-2 and shows a word fewer times for the same retention, and the algorithm and its default parameters are public. We use SM-2 (`src/sm2/sm2.ts`, a port of the Flutter app's `Word.applyReview`) only because the frozen Flutter app wrote the same `user_progress` rows; that constraint is gone. What the migration touches: `user_progress` carries `ease_factor`, `interval` and `repetitions`, which FSRS replaces with stability and difficulty (plus a last-review time and a lapse count), so it needs new columns and a rule for converting every existing row (roughly: stability from the current interval, difficulty from the ease factor) that neither resets anyone's progress nor makes a whole backlog come due at once. It also reaches everything built on SM-2's fields: the interval previews on the rating buttons, the relearning step and the state Learn leaves a word in (`repetitions 1, interval 0`), the Words screen's stages ("In progress" is `repetitions` 1, "Known well" is 2 or more), the review ordering (most overdue first could become least likely to be remembered first), the write queue's progress upsert and the restore rules, and the tests around all of it.
- **A shared pool of user-contributed words.** A word a user adds can also go to a public list that other users can take into their own vocabulary.
- **Rejected, measured: a regional preference (Argentine or Uruguayan).** The idea was a setting so a card that leads with "ómnibus (uy), also colectivo (ar)" would lead with the other form for someone who picks Argentina. The count that decides it was made on the shipped overlay (`public/rio_overlay.json`): one entry out of 76 has two regional variants, autobús (ómnibus / colectivo), the only pair that two independent families of sources agree on for both countries. One word is far too few to justify a row in Settings, so it was not built; do not reopen it from scratch. Worth revisiting only if the overlay grows several times over (a few hundred entries, so that there are dozens of such pairs). The count has fallen as the data was checked: it first read five, because foco carried an `alt_form` ("lámpara") with no country, which was one respondent's own word and not a regional variant; then four, and then one, when the country labels were put under the two-source rule and the pairs guay / copado, portero / arquero and asilo / geriátrico were found to rest on a single source (for copado and arquero the other sources say both countries use the word).
- **Method: the questionnaire only asked Uruguayans, so it cannot establish that a form is Uruguay-only.** Every question was "¿En Uruguay …?", asked of 8 Uruguayans: it shows that Uruguayans use a word, never that Argentines do not. The overlay used to set `region: 'uy'` by rule on that evidence alone, and ten entries carried a country label nobody had earned; they are now null unless two independent families of sources say the other country does not use the form (`tools/rio-overlay/regionRule.mjs`). A future round has to ask Argentines the same questions, or the data will keep carrying this asymmetry: until then a label can only come from the model runs and DAMER, never from the questionnaire.

- **Real statistics.** Today the app shows a streak and seven activity dots. Worth having: how many words are known at each stage, a forecast of the coming review load (how many reviews fall due each day over the next weeks), retention over time, and the words that keep lapsing. `user_daily_metrics` already records per-day activity (new words, reviews done, reviews lapsed, how many were due at the start of the day, the learn pool and the daily limit), so some of this needs no new writes: the history of the review load, a rough retention curve (1 − lapsed / done per day) and the new-word pace. The words that keep lapsing are the exception: a lapse is counted per day, never per word, so that one needs a lapse count on the progress row (which FSRS wants as well, see the FSRS entry).
- **Pronunciation (to be discussed before building: the most expensive item here).** This entry records the question, not an answer. Recorded native audio or text-to-speech? Native audio sounds best but costs a speaker's time for every word, and a speaker whose Spanish is Rioplatense; text-to-speech is cheap and covers any word, including the ones users add, but is there a voice that is acceptable for Rioplatense (the "ll" and "y" sound, voseo forms)? What it costs: recording or generating audio for the roughly 4,700 dictionary words (and the example sentences?), and a running cost if speech is generated on demand. Where it lives: files in `public/` next to the dictionary, or a storage bucket, with the size and the offline behaviour that follow. And what it covers: every word, or only the Rioplatense overlay entries (76 today), where the pronunciation is the furthest from what a learner expects of textbook Spanish.
- **Phrases, not only single words.** The add-word form rejects anything with a space (`checkSpanish` in `src/data/customWords.ts`, inherited from the Flutter app; the proxy's `/enrich` does not). Users will ask for "estar seguro", "de una", "ni ahí". Lifting the restriction touches the duplicate check (`findDuplicate` matches a typed word against es_word and the overlay forms), the headword rule (what leads a card and what is highlighted in its example), enrichment (the prompt asks about a word, and `word_form_in_example` must be an exact substring of the example) and Cloze (what gets blanked). The overlay already has multi-word forms ("de más", "casa de salud", "con vos"), so part of this exists. It is also the honest answer to word senses: "estar seguro" as its own entry beats splitting "seguro" into meanings.
- **The reverse direction: Russian or English to Spanish.** Everything the app does today trains recognition: Learn shows a Spanish word with its meaning, and Review and Matching ask for the meaning of a Spanish word. Only Cloze asks for production, and then with a cue (the sentence around the blank). A reverse card shows the meaning and asks the user to recall the Spanish word, which is the skill people actually complain about missing. It needs a decision first: a separate mode, or reverse cards mixed into Review? And whether a reverse card carries its own SM-2 state or shares the word's: recognising a word and producing it are different memories, so sharing would schedule one by the other, while its own state means a second row per word, and `user_progress` is keyed on (user_id, es_word), so the key needs a direction. Two smaller questions come with it: a meaning is often shared by several Spanish words (and by a word's Rioplatense and standard forms), so what counts as the right answer; and how the answer is given, typed or self-rated.

- **Low priority — let the user choose the reminder hour.** It is a module constant, `REMINDER_HOUR = 20` in riopalabras-proxy `reminders.js:10`, the same for everyone and applied in each user's own time zone (taken from their `reminders` row), so the one thing that varies per user today is which UTC instant their local 20:xx is. Making it per-user takes a column on `public.reminders` (an hour from 0 to 23, with a check), a control in Settings → Notifications that the user may write (the column privileges and the RLS policy in the proxy's `sql/reminders.sql` allow only `enabled` and `timezone` now, so the grant is extended, and the line under the toggle, which says "at 20:00", has to say the chosen hour in both languages), the job comparing the local hour with the row's hour instead of the constant, and a migration that gives every existing row 20 (a `default 20 not null` does it). A natural candidate for the paid tier: it is a small, visible convenience that costs nothing to run.
- **Closed: a reminder with no usable time zone used to be skipped for good, and nothing said so; it now falls back to UTC.** `localParts()` returns null for a missing, empty, non-text or unrecognised zone, and `schedule()` used to answer `no-timezone` for it, so the row was left alone every hour, forever, and the only trace was `skipped['no-timezone']` in the job's log. The job now reads such a row in UTC (`localFor()` in riopalabras-proxy `reminders.js`): the reminder goes out at 20:00 UTC, and `last_sent_on` is that row's UTC date, so the same-day guard works as it does for any row. It is a fallback, not a default: a row with a usable zone is untouched, and the skip reason is gone from the code, since nothing could reach it. It is visible in the two places the skip was not: the summary counts these rows in `fallbackZone` (not a bucket: such a row is still settled in exactly one, and `unaccounted` stays 0), and the dry-run line says `tz=UTC (fallback: the zone "…" is unusable)` with the value that failed; a normal run also logs one line for each such row it actually messages. **Why the fallback and not surfacing it in Settings → Notifications.** The case is rare, because the client writes the device's zone when the reminder is turned on and at every app open if it differs from the row's, which also fills in a row that has none, so it mends itself at the next open; for a person it has not mended, a reminder at an hour nobody chose (20:00 UTC is 17:00 in Montevideo, 23:00 in Moscow) is better than none, and for most of the people this app is for (Uruguay, Argentina, Russian-speakers in Europe) it is still an hour they are awake, so it costs little. A line in Settings would need a client change, two strings and tests, for a state the person can do nothing about (the zone comes from the device), and it would leave the row silent until they happened to open Settings. **What is left.** A row can still get a reminder at an odd hour: far enough east (Asia, Oceania) 20:00 UTC is the small hours or the morning. And a row that is mended the same day it was messaged on the fallback can be messaged once more that day: its recorded day is the UTC date, which for a zone far east of UTC is not its local date. If `fallbackZone` is ever non-zero for long, the cause to look at is a device that reports no zone at all, and then the Settings line (the other option) is worth building.
- **A frequency label on words.** The dictionary is already ranked by frequency, and the rank drives which words Learn offers (`compareByRank`, the placement test's `startRank`) and is the word list's default sort (`'frequency'` in `src/data/wordList.ts`), but nothing on a card or in a list row says how common a word is. The idea: a small label on the word card and in the word list with three states at most, "top 1000", "common" (to rank 5000) and nothing beyond that, where having no label means something in itself (a word the user will rarely meet). In the word list the label should also make sorting and filtering meaningful: filter to "top 1000" or to "common", and sort within a band. **Check the thresholds against the data first.** The shipped dictionary has 4,753 entries and its highest rank is exactly 5000, so with those numbers "nothing beyond rank 5000" would label no dictionary word at all: only a user's own words (they have no rank) would go unlabelled, and "common" would be nearly everything that is not top 1000 (991 words are at or under rank 1000, 2,910 at or under 3000, all 4,753 at or under 5000). A cut that leaves the missing label meaning something needs a lower second threshold (3000 leaves about 1,800 words unlabelled); or the absence is simply "your own word", which is also a meaning. **Two caveats.** The rank is for Spanish in general, not Rioplatense, and it belongs to the dictionary's standard word, so on the cards that lead with a local form it can mislead. The card for "chico" (rank 109) leads with "gurí", and "autobús" (rank 1567) with "ómnibus": a frequency label there would call the card "top 1000" on the strength of a word the card is not showing, and say nothing true about gurí or ómnibus, which are not in the frequency list at all (neither are bondi, boliche, botija, chacra or campera). So the absence of a label would read as "rare" for words that are everyday in Uruguay, and a user's own words (no rank) would read the same way. Those words probably want a label of their own ("Rioplatense", which the overlay already knows: 76 entries carry it) in place of a frequency one, or beside it, rather than a frequency band they have not earned. And the label has to agree with the word list's own controls: the frequency sort and any new filter must use the same bands, so that "top 1000" in a list is exactly the words that carry the label on their cards.
- **Widen the word-of-the-day pool.** The pool is 71 words today: the overlay entries whose card can highlight an example (76 overlay entries, minus five kept off Home as vulgar, offensive or pejorative), so the cycle is 71 days and a user who stays more than two and a half months sees every word again. The word of the day should stay Rioplatense in character, so the answer is not to open it to the whole dictionary. The idea to record: keep the overlay words as the core, and extend the pool with rare words (rank 3000 and above) and with words the community has contributed, so the cycle becomes long without the word of the day turning into an ordinary common word. **Needs the community contribution feature to exist first** (see "A shared pool of user-contributed words"); the rare-word half does not, and could ship alone. **What the data says about the rare half.** 1,813 dictionary words have a rank of 3000 or more and are not overlay entries; every one of them has an example that can be highlighted, so all would qualify (the cycle would become 1,884 days, about five years). But the sample is ordinary Spanish (avenida, índice, literario, conquistar, notable): they are rare, not Rioplatense, and added at that size the Rioplatense words would be 71 of 1,884, under 4% of the days. So the idea as worded keeps the character only if the core is weighted, for instance an overlay word every other day with the rare and contributed ones filling the days between (the overlay words then recur about every 142 days, and the cycle is the length of the longer list), or a small band of rare words only (say 3000 to 3500), or rare words that the overlay also marks as Rioplatense in some way. Three things to settle first. **The register filter:** only overlay entries carry a register, which is how the five unfit words are kept off Home; a dictionary word outside the overlay has none, so a vulgar or offensive rare word could come up on the home screen, and the rare words need checking (or a register) before they go in. **A one-time reshuffle:** the order is a permutation by hash of each word's name indexed by the day number modulo the pool's size, so growing the pool changes the divisor and moves every day's word once, on the day it ships; and a community pool grows all the time, so it would move them every time unless the day-to-word mapping stops depending on the pool's size (an append-only list indexed from a fixed start day, say). **Whose words:** contributed words need the same checks as the rest (an example that highlights, a register) and a say for the user, since a word they hid is already skipped (hiding a word changes only its own days, see the word-of-the-day order in `src/data/wordOfDay.ts`).
- **More examples for a word, on request: half one, for the user alone.** A word has exactly one example today (the overlay's, or the dictionary's), and in Cloze that is a problem: after a few showings the user has memorised the sentence as a whole, and filling the blank no longer tests the word, only the sentence. The idea: a button on a word that asks for one more example, generated through the existing `/enrich` path in riopalabras-proxy (it already returns a sentence, its translations and `word_form_in_example`, and the proxy already checks that the form is a substring of the sentence), and saved for that user only. That needs somewhere to keep it (a small per-user table of extra examples, which the client merges onto the word the way it merges custom words and progress), Cloze choosing among a word's examples and not repeating the one it showed last, and the word card showing one of them. A candidate for the paid tier, with a small daily allowance on the free tier and not none, so everyone sees what it does; see "Decide what goes behind premium". Its allowance should be its own counter: the proxy's daily limit is 100 words per user and 2,000 calls across everyone (`quota.js`), which is sized for adding words, and an example costs the same call as a word does. This half does not need the other.
- **More examples for a word: half two, contributing a generated example to everyone (not built, and not promised by half one).** A generated example that turns out well could go to the shared dictionary for all users. Say the risk plainly: an unreviewed example can be ungrammatical, not Rioplatense, or simply poor (the prompt asks for Rioplatense Spanish and the proxy checks the form is in the sentence, which says nothing about whether the sentence is good), and once a poor one is in the shared dictionary it is fixed one word at a time, by someone reading each. So if this is ever built it should be a submission that waits for review (the same review the user-contributed words need, see "A shared pool of user-contributed words"), and never a direct write to the shared dictionary. It depends on half one, and on that review existing.
